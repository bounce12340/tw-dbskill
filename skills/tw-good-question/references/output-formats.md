# 輸出格式模板

預設輸出寫在 `SKILL.md`。以下格式按條件使用；空的小節不寫，未知項寫「未知」。

## 嚴格問題品質審計

只有使用者要求「嚴格審計」「打分」「判斷問題品質」時使用。

```markdown
# 好問題診斷

## 原問題
{使用者原話}

## 當前評分
| 檢查項 | 得分 | 說明 |
|---|---:|---|
| 物件 | 0-2 | |
| 目標 | 0-2 | |
| 衝突 | 0-2 | |
| 約束 | 0-2 | |
| 反饋 | 0-2 | |

總分：{x}/10

## 最大缺口
{最影響 Agent 推理的缺口}

## 改寫成好問題草案
{問題說明書草案}

## 最小下一步
{一個動作。需要使用者補資訊時，列 0-3 個會改變判斷的問題}
```

## Agent 可解性判斷

使用者問某個任務能不能由 Agent 自動完成時使用。

```markdown
# Agent 可解性判斷

## 結論
{A / B / C / D 檔}：{一句話說明}

## 為什麼
| 判斷項 | 結果 | 說明 |
|---|---|---|
| 邊界清楚 | 高 / 中 / 低 | |
| 變數可表達 | 高 / 中 / 低 | |
| 反饋可獲得 | 高 / 中 / 低 | |
| 解釋可檢驗 | 高 / 中 / 低 | |
| 行動可執行 | 高 / 中 / 低 | |
| 規律穩定 | 高 / 中 / 低 | |

## 可自動化部分
{Agent 可以直接做什麼}

## 需要人類介入的部分
{哪些判斷、資源、反饋必須由人提供}

## 最小下一步
{先做什麼}
```

## 完整問題說明書

清晰度高，或使用者要一份可直接交給 Agent 的說明書時使用。

```markdown
# 問題說明書

## 我要分析的問題
{一句話問題}

## 現象
{具體發生了什麼}

## 目標
{解釋 / 預測 / 改進 / 決策}

## 核心衝突
{哪裡和預期不一致}

## 背景事實
{事實、資料、上下文}

## 約束
{不能改變什麼，必須考慮什麼}

## 反饋入口
{可以觀察什麼、收集什麼、測試什麼}

## 請 Agent 做
1. 生成 2-3 個候選解釋。
2. 用 hard to vary、可檢驗性、行動指向批評每個解釋。
3. 選出最值得驗證的解釋。
4. 給出一個最小驗證動作。
```

「請 Agent 做」可以按使用者任務改寫，但要保留候選解釋、批評、選擇和最小驗證動作的鏈條。

## 候選解釋與批評

清晰度達到 8 分以上，或使用者明確要求候選解釋時使用。

```markdown
# 候選解釋與批評

## 當前問題
{已經釘住的問題}

## 候選解釋
1. {解釋 A}
2. {解釋 B}
3. {解釋 C，可選}

## Hard to Vary 對比
| 候選 | 機制 | 排除項 | 可驗證訊號 | 行動變化 | 評分 |
|---|---|---|---|---|---:|

## 當前最強解釋
{最 hard to vary 的解釋}

## 仍然不確定的地方
{不能假裝確定的部分}

## 最小驗證動作
{下一步做什麼}
```
