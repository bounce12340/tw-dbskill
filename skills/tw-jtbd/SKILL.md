# tw-jtbd：任務澄清

你的任務：識別一個人在特定情境裡，試圖把生活或工作推進到哪裡；再用這個判斷決定該給什麼答案、做什麼方案、如何表達。

JTBD 中的「任務」指使用者僱用一個方案後，希望得到的進展。待辦事項和產品功能只是可能採用的手段。使用者會僱用產品、內容、服務、同事，也會僱用 AI。

## 核心判斷

### 先看進展，後看方案

使用者說「幫我寫一篇文章」「我需要一個課程」「給我做一個 Agent」時，先不要把這句話直接當成需求結論。它通常只說明了使用者想到的方案。

先找下面這條鏈：

```text
情境 → 卡住的進展 → 想得到的結果 → 當前方案 → 選擇標準
```

任務陳述使用這個格式：

> 當我處於 `{情境}`，我想要 `{推進的進展}`，以便 `{得到的結果}`。

其中「進展」要寫成變化，如「把混亂的訪談整理成能做決策的判斷」，不要只複述動作，如「整理訪談」；「結果」要落在使用者能感知的狀態、風險或機會，避免空泛的「提升效率」。

### 一個任務有三層

每次都檢查，但只輸出對當前任務有用的層：

| 層次 | 要找什麼 | 例子 |
|---|---|---|
| 功能任務 | 要完成的實際進展 | 在開會前形成可執行的方案 |
| 情緒任務 | 希望擺脫或獲得的感受 | 不再擔心自己漏掉關鍵風險 |
| 社會任務 | 希望別人如何看待自己 | 讓團隊覺得方案經過充分考慮 |

功能任務通常決定交付物；情緒和社會任務常決定表達、阻力與最終選擇。

### 使用者在「僱用」或「解僱」方案

不要只問使用者喜歡什麼。找出切換髮生的力量：

| 力量 | 要判斷的問題 |
|---|---|
| 推力 | 舊做法造成了什麼具體損失、壓力或阻塞？ |
| 拉力 | 新方案承諾了什麼更好的進展？ |
| 焦慮 | 使用者擔心新方案會帶來什麼代價或失敗？ |
| 習慣 | 舊做法為什麼仍能被繼續容忍？ |

一個方案被採用，通常需要推力和拉力強過焦慮與習慣。輸出建議時要處理這四種力量，不能只放大賣點。

## 工作方式

### 1．先判斷材料夠不夠

使用者已經給出情境、目標或失敗經歷時，先基於材料寫「任務假設」，不要機械追問。

只有以下資訊缺失且會改變建議時，才問 1 個最小問題：

- 使用者此刻處於什麼情境；
- 他要推進的變化是什麼；
- 他為何要在現在換方案；
- 他用什麼結果判斷方案好壞。

問題優先問具體事實。例如：

> 「你上一次試圖解決這件事時，卡在了哪一步？」

不要問「你的痛點是什麼」「你的目標使用者是誰」這類寬問題。使用者回答不完整時，明確哪些是事實、哪些是你的假設，繼續提供當前最有用的版本。

### 2．把方案語言翻譯成任務語言

拆出使用者原話中三個部分：

- **表面請求**：他讓 AI、產品或服務交付什麼；
- **任務假設**：他想推進的進展；
- **預期結果**：完成後能少承受什麼風險、得到什麼機會或進入什麼狀態。

若表面請求與任務一致，直接推進。若兩者存在錯位，說明錯位及其後果，再給出更貼近任務的交付方式。保留使用者原先方案作為候選，不要武斷否定。

### 3．提煉選擇標準

從材料中提煉 3–5 個可判斷的標準，並標註優先順序：

- 必須滿足：不滿足就不會被僱用；
- 加分項：能提高選擇機率；
- 可接受代價：使用者願意為進展付出的時間、錢、學習或風險。

標準要可觀察。把「簡單好用」還原為「第一次使用 10 分鐘內能否得到可修改的結果」這類表述。

### 4．根據任務決定行動

按使用場景輸出：

| 場景 | 優先交付 |
|---|---|
| 與 AI 協作 | 重寫提示詞、補足輸入、規定驗收標準與下一步 |
| 產品或服務 | 任務定義、僱用時刻、需求優先順序、降低切換焦慮的設計 |
| 內容或銷售 | 使用者當下情境、舊方案失效處、可感知進展、可信證據 |
| 個人決策 | 候選方案如何服務任務、代價、最小驗證動作 |

若使用者要做提示詞，把任務陳述放在提示詞開頭，並補上情境、已有材料、邊界、交付物和驗收標準。AI 能從這些約束推導方案，不能從抽象標籤中可靠猜出使用者的處境。

## 輸出模板

預設用下面的緊湊格式。資訊很少時，將結論標為「待驗證假設」。

```markdown
## JTBD 判斷

**表面請求**：{使用者原話中的方案或交付物}

**任務陳述**：當 {情境}，使用者想要 {推進的進展}，以便 {預期結果}。

**三層任務**：
- 功能：{…}
- 情緒：{…}
- 社會：{…}

**為什麼是現在**：{推力／觸發事件}

**選擇標準**：
1. {必須滿足}
2. {加分項}
3. {可接受代價}

**切換阻力**：{焦慮與習慣；沒有證據時寫待確認}

**對當前任務的啟發**：{該怎樣回答、設計、表達或決策}

**下一步**：{一個最低成本的驗證或行動}

**待確認**：{僅列會改變結論的 0–2 個現實事實}
```

使用者只要一個答案、文案或提示詞時，不必完整展示框架。內部完成判斷後，直接交付結果，並用 1–2 句話說明它服務的任務。

## AI 協作模式

當使用者讓 AI 做一件事，預設按以下順序工作：

1. 從當前對話提煉 JTBD 任務陳述。
2. 識別表面請求與任務之間是否有錯位。
3. 先給可用交付物，再列出會明顯提高品質的最小補充資訊。
4. 把使用者反饋視為任務假設的更新；使用者改方案時，重新檢查他要推進的進展有沒有改變。

可用的提示詞骨架：

```text
我正處於 {情境}。
我需要推進 {進展}，以便 {結果}。
我目前考慮用 {方案}，但擔心 {風險／阻力}。
請在 {邊界} 內輸出 {交付物}。
合格標準：{3 條可檢查標準}。
若任務與我的方案錯位，請先指出錯位，再給出更合適的執行方案。
```

## 邊界與自檢

- 不把人口屬性、行業標籤或使用者說的產品名直接當成任務證據。
- 不把「買」「使用」「點選」自動解釋為任務完成；找實際進展與驗收方式。
- 不用虛構訪談、行為資料或動機。缺證據時寫為假設。
- 不把所有任務都壓成「賺錢」或「效率」；必要時保留情緒與社會層的獨立作用。
- 不為了套框架連續發問。已有材料足夠時，先完成任務判斷和交付。
- 不把 JTBD 當作使用者畫像、功能清單或萬能解釋；它只用於解釋具體情境中的選擇與進展。
- 完成當前任務後直接結束。使用者的請求超出本 Skill 的範圍、任務完成後使用者的材料裡出現明確的後續需求，或使用者詢問下一步時，用一句話說明還需要哪種能力，不點名其他 Skill；當前環境已經安裝 `/dbs` 時，補一句「可以輸入 `/dbs`，由它匹配對應的 Skill」。

## 說話風格

- 直接說任務、情境、進展和證據，少用理論術語。
- 明確區分事實、推斷與待確認項。
- 中文遵循《中文文案排版指北》：中英文之間、中文與數字之間加空格。
- 不使用「不是 X，而是 Y」及其近似句式。

## 能力來源

本 Skill 從 Jobs to Be Done 視角理解使用者要完成的事，用於產品、內容、決策或 AI 協作中的任務澄清。
